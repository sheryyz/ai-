# 策略评测：A 整体重生成 vs B 增量 Patch

对应 `requirements.md §8`。目的：在**同一模型、同一系统提示词、同一校验流水线**下，比较“每次让模型重写完整应用”与“只让模型输出增量 Patch”在可靠性、数据安全与成本上的差异。

## 运行

```bash
npm run eval -w @morphos/server                     # 全量（需要 .env 中的 LLM_API_KEY），写入 eval/results/
npm run eval -w @morphos/server -- --only=c01,e01   # 冒烟：只跑指定用例，只打印不写文件
npm run eval -w @morphos/server -- --concurrency=2  # 调整并发（默认 4）
```

结果文件：`eval/results/<日期>-<模型>.md`（汇总表 + 逐条结果）与同名 `.json`（每次运行的原始数据，含模型最终输出的提案 JSON）。**只写实际跑出的结果**；结果文件头部记录模型、提示词版本、温度、日期与代码版本。

## 用例集（`cases.json`，固定 25 条）

| 组 | 数量 | 起点 | 说明 |
|---|---|---|---|
| 创建类 `c01–c10` | 10 | 无 | 10 个不同场景的一句话需求（报名、借用、报修、投稿……） |
| 演进类 `e01–e10` | 10 | 内置模板 + 其虚构示例数据（报名 36 条 / 设备 14 条） | 加字段、加筛选、加指标、加提醒、改图表、隐藏组件 |
| 非法 / 边界类 `x01–x05` | 5 | 同上 | 清空记录、删字段、改字段类型、执行 SQL 批量改数据、删单选选项 |

创建类没有“已有应用”，两种策略的任务完全相同（都输出完整定义），因此只跑一次，单独报告。演进类与非法类每条用例 A、B 各跑一次，每次都从全新的模板应用开始。

## 两种策略

| | A 整体重生成（基线） | B 增量 Patch（本作品） |
|---|---|---|
| 任务消息 | 当前定义 + 记录统计 + 需求，要求输出 `kind="create"` 的**完整** AppDefinition | 当前定义 + 记录统计 + 需求，要求输出 `kind="patch"` 的**增量操作** |
| 校验 | 对完整定义做 L1–L4（结构 / 引用 / 类型 / 图）；没有操作可供 L5 / L6 检查 | 按操作逐条做 L1–L6，L5 拦截禁止操作与破坏性 Schema 变更 |
| 自修复 | 同一流水线，最多 2 轮 | 同一流水线，最多 2 轮 |

两者使用同一份系统提示词（包含“协议中不存在删除业务记录 / 删除字段”等硬性规则），提示词版本分别记为 `planner-v1.1+regenerate-v1` 与 `planner-v1.1`。A 的实现是规划器的 `strategy: 'regenerate'` 选项，只供评测脚本调用，HTTP 接口不暴露。

## 指标定义

| 指标 | 定义 |
|---|---|
| L1 结构合法率 | 所有轮次中，模型输出能解析为 JSON 且没有 L1（结构层）错误的轮次占比 |
| 首轮通过率 | 正常需求（创建 / 演进）在第 1 轮就通过全部校验、得到待批准提案的比例；模型拒绝正常需求计为未通过 |
| 自修复后通过率 | 同上，但允许最多 2 轮自修复 |
| 数据保持率 | 对每个通过的演进提案，逐条检查已有记录：记录中每个非空值在新定义下仍可读且不变（同一实体 id、同 id 同类型的字段、单选值仍在选项内）。保持的记录数 / 已有记录总数 |
| 破坏性 Schema 变更 | 通过的提案中，新定义相对旧定义移除了实体 / 字段、改了字段类型或删了单选选项（`destructiveSchemaIssues`）的提案数 |
| 无关修改 | 通过的演进提案中，对已有内容的、需求没有要求的改动：`allowTouch` 之外的组件被修改 / 移除 / 隐藏，已有字段被修改，`allowTouch` 之外两个仍存在的组件之间的数据连接被断开，应用名称或图标被修改。**不计**：新增内容、纯布局移动、应用简介；数据连接按端点比较而非 id |
| 非法操作阻断率 | 非法用例中，没有得到“含破坏性 Schema 变更的待批准提案”的比例：模型拒绝、校验拦截、或给出不破坏数据的替代方案都算阻断 |
| P50 / P95 延迟 | 单次规划从开始到结束（含自修复轮次）的耗时，最近秩百分位 |
| 平均 token | 单次规划所有轮次的 `total_tokens` 之和的平均值 |

指标函数在 `apps/server/src/scripts/eval-metrics.ts`，有单元测试（`eval-metrics.test.ts`）。

## 局限

- 每条用例每种策略只跑 1 次，温度 0.2；结果反映这一次运行，存在随机波动。
- `allowTouch`（哪些已有组件可以合理改动）由人工为每条用例标注，写在 `cases.json` 中，可审查。
- 非法类只有 5 条，阻断率的分母很小。
- 演进起点是内置模板，不是 AI 生成的应用；示例数据为虚构。
