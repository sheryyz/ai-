模型输出只作为数据解析；无 `eval`、无动态 SQL；SQL 全部使用参数化语句。\n- 服务端对所有写入按当前 Schema 重新校验，前端校验仅为体验。\n- 批准提案时在事务内重新校验并检查 `baseVersion`，防止并发覆盖。\n- 模型调用设置超时、单次请求 token 上限、自修复轮数上限，避免死循环与费用失控。\n- 请求体大小限制；记录数量、节点数、绑定数有上限。\n- 用户用自然语言获得一个真正能录入、保存、筛选、统计、导出数据的小应用；之后继续用自然语言提出新需求，应用在**保留全部业务数据**的前提下，经过**校验、预览、人工批准**持续演进，并可恢复到任一历史界面配置。\n\n**修正 6：一份数据，按角色长出不同的页面。** 组织者一句话就能给某一类人（报名者、志愿者、借用人……）生成专属页面，通过分享链接使用。每次 AI 改动上线前，系统**算出**每类人能看到什么、能改什么；越过用户声明的界限就拦下，公开敏感信息必须由人确认。\n\n核心理念：**用户表达意图 → AI 编排应用 → 系统验证变更（含谁能看到什么）→ 用户确认 → 应用持续运行，各角色各用各的页面。**\n\n## 2. 痛点（修正 1：从“搭建成本”具体化为“数据断裂”）\n\n以一场 120 人的校园讲座为例，组织者在三个阶段要用四种工具：\n\n| 阶段 | 常用工具 | 断裂点 |\n|---|---|---|\n| 筹备 | 问卷星收报名 | 导出 Excel |\n| 整理 | Excel 管名单 | 手工去重、加列 |\n| 现场 | 纸质表 / 小程序签到 | 签到结果与名单分离 |\n| 跟进 | 微信群逐个提醒 | 要先人工找出谁没到 |\n\n**每换一个阶段，数据就断一次。** 临时需求（“找出计算机专业还没签到的人，提醒他们”）没有任何一个工具能直接完成，只能手工拼表。实验室设备借用、社团物资管理有完全相同的结构。\n\n**断裂还带来泄露。** 为了让志愿者在门口签到，组织者往往把整张报名表（含所有人的手机号、学号）发到群里；为了让报名者确认“我报上了没有”，又把名单截图公开。每个环节的使用者需要的只是名单的一小部分，现有做法却是整份数据随手转发。\n\nMorphOS 的回答：**一套数据贯穿始终，工具随需求演进，而不是数据随工具迁移；每类人只拿到自己需要的那一部分，而且给多少是算出来、看得见的。**\n\n## 3. 差异化（修正
