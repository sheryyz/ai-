---

## 1. 一句话定义

面向校园活动全生命周期管理，构建一个能理解自然语言任务、动态组合真实业务能力、自动关联现有数据，并支持变更预览与界面版本回滚的智能工作台。

**用户不再适应软件的固定菜单，软件根据用户当前任务组装出可执行的工作界面。**

---

## 2. 痛点与差异化

### 2.1 真实痛点：工具切换导致数据断裂

一个校园活动组织者在筹备、现场、复盘三个阶段要用三四个工具：问卷星收报名、Excel 管名单、微信群发通知、纸质表或小程序签到。名单在工具之间反复导出导入，每换一个阶段数据就断一次，出错率高，临时需求（如「找出没签到的人发提醒」）要手工拼表。

### 2.2 为什么不是「普通活动平台 + AI 切换 Tab」

| | 普通活动管理平台 | MorphOS |
|---|---|---|
| 功能形态 | 固定 N 个功能入口 | 少量能力 × 开放参数 × 任意数据绑定 |
| 临时需求 | 没有对应菜单就做不了 | 自然语言描述，AI 组合现有能力生成新工作区 |
| 变更透明度 | 无 | 每次变更先出 Morph Diff，用户批准后生效 |
| 可逆性 | 无 | 界面配置版本化，可撤销、可对比、可溯源到触发意图 |
| 数据 | 分散在多个工具 | 一套持久数据贯穿全流程，永不迁移 |

**标准口径：** 开放参数指 AI 生成的筛选表达式与消息模板（如「报名早于 11 月 15 日、未签到、计算机专业」），这不是菜单能穷举的；任意绑定指组件之间的数据流边由 AI 按意图建立，并经过校验。

### 2.3 核心主张（技术文档首页）

MorphOS 不是三个功能，是一条流水线：
**意图理解 → 能力组合 → 数据绑定 → 变更验证 → 人工确认 → 真实执行 → 版本记录**

## 3. 演示主线（唯一闭环，做完整、做稳定、做漂亮）

1. **初始化**：输入「我要办一场 120 人的校园科技讲座，需要收报名」→ 生成活动概览 + 报名表单 + 名单 + 统计的筹备工作台。
2. **真实数据**：通过公开报名链接填入若干报名，名单与统计实时更新，刷新页面数据仍在。
3. **现场新需求**：输入「活动马上开始，找出还没签到的人，生成提醒内容，旁边显示实时签到率」。
4. **Morph Diff**：系统展示提案：新增智能筛选（未签到）、消息编辑（收件人绑定筛选输出）、实时统计（签到率）；复用 attendees 数据；保留 checkinRecords；验证通过。
5. **确认与执行**：用户批准 → 界面变形动画 → 新工作区可直接操作：签到几个人，未签到名单与签到率同步变化，消息草稿生成并通过「模拟发送通道」记录。
6. **被拒绝的变更**（30 秒，必拍）：输入「把没来的人从名单里清掉」→ 提案涉及删除报名记录 → Validator 拦截并说明原因 → 用户改为「隐藏未签到人员」→ 通过。
7. **回滚**：撤销上一次界面变更 → 布局恢复，**已发生的签到记录与消息记录不受影响**。
8. **演进历史**：时间线展示每个版本、触发意图、Diff 与验证结果。

## 4. 功能范围

| 优先级 | 功能 | 验收标准 |
|---|---|---|
| P0 | 自然语言初始化工作台 | 一句话生成可用的筹备工作台，含真实可填的报名表单 |
| P0 | 意图驱动的动态功能组合 | 对未预设的需求，AI 生成含 bindings 的 Patch，渲染出可操作的新工作区 |
| P0 | Morph Diff 可解释变更 | 变更前展示新增 / 调整 / 保留 / 验证结果，支持批准、继续修改、拒绝 |
| P0 | 界面版本历史与回滚 | 撤销后布局与绑定恢复，业务数据不变 |
| P0 | 一套数据贯穿全流程 | 报名、签到、消息记录持久化于 SQLite，刷新与阶段切换均不丢失 |
| P0 | Validator 拦截非法变更 | 组件不存在、端口类型不匹配、涉及删除业务数据的 Patch 被拒绝并给出可读原因 |
| P0 | 确定性演示模式 | 无 API Key 时可完整复现主线，界面明确标注「演示模式」 |
| P1 | 基于业务事件的主动建议 | 仅一条规则：活动开始时间到达 → 弹出「切换到现场工作区」建议。做不完即删 |
| P2 | 拖拽反向推断意图 | 省赛不写一行代码，写入国赛规划 |
| P2 | 多场景支持 | 国赛扩展 |
| 不做 | AI 生成任意可执行代码 | 架构层面禁止 |
| 不做 | 真实短信 / 微信发送 | 用站内消息记录 + 一键复制替代，界面明确标注「模拟发送通道」 |

## 5. 架构

### 5.1 流水线

```
用户自然语言 / 业务事件
        │
        ▼
Intent Engine     提取任务目标、约束、引用的数据实体，结合当前界面状态
        │
        ▼
Morph Planner     大模型输出结构化 Patch（JSON，受 Schema 约束）
        │
        ▼
Validator         Zod 结构校验 + 语义校验（组件注册表、端口类型、绑定图无环、业务数据保护）
        │
        ▼
Morph Diff UI     展示新增 / 调整 / 保留 / 验证结果 → 批准 / 继续修改 / 拒绝
        │
        ▼
UI Renderer       按组件注册表渲染，Framer Motion 变形动画
        │
        ▼
Data & Actions    真实 CRUD（报名、签到、消息记录）
        │
        ▼
Version History   记录版本、触发意图、Patch、验证结果
```

### 5.2 Patch 协议（草案，最终以 `schema/patch.schema.json` 为准）

```json
{
  "intent": "活动马上开始，找出未签到人员，生成提醒，显示签到率",
  "rationale": "需要筛选、消息、统计三项能力并建立数据流",
  "operations": [
    { "op": "add",  "id": "f1", "component": "SmartFilter",
      "props": { "source": "attendees", "expr": "checkedIn == false" } },
    { "op": "add",  "id": "m1", "component": "MessageComposer",
      "props": { "template": "{{name}} 同学，讲座即将开始，请尽快到场签到" } },
    { "op": "add",  "id": "s1", "component": "LiveStats",
      "props": { "metric": "checkinRate" } },
    { "op": "bind", "from": { "node": "f1", "port": "rows" },
                    "to":   { "node": "m1", "port": "recipients" } },
    { "op": "move", "id": "s1", "region": "sidebar" },
    { "op": "hide", "id": "registrationForm" }
  ],
  "preserve": ["attendees", "checkinRecords", "messages"]
}
```

允许的 op：`add` `move` `hide` `show` `remove`(仅限非数据承载组件) `bind` `unbind` `setProps`。
**不允许任何 op 触碰业务数据表。** 业务数据只能通过组件内的真实操作改变。

### 5.3 组件注册表（8 个，每个声明输入 / 输出端口）

| 组件 | 作用 | 输入端口 | 输出端口 |
|---|---|---|---|
| EventOverview | 活动信息、阶段、倒计时 | - | - |
| RegistrationForm | 公开报名表单（可生成链接） | - | - |
| AttendeeTable | 人员名单，支持列选择 | rows | selectedRows |
| SmartFilter | AI 生成的筛选表达式（安全 DSL，非 eval） | source | rows |
| QuickCheckIn | 搜索 / 扫码签到，写 checkinRecords | - | - |
| LiveStats | 签到率、报名数等实时指标 | rows(可选) | - |
| MessageComposer | 收件人 + 模板 → 草稿 → 模拟发送记录 | recipients | - |
| ActivityLog | 业务操作与界面演进时间线 | - | - |

### 5.4 Validator 规则

1. 组件名必须在注册表中。
2. bind 的端口必须存在且类型匹配（rows → rows / recipients）。
3. 绑定图必须无环。
4. 数据承载组件只能 hide，不能 remove。
5. Patch 不得包含对业务数据的删除、清空、重建语义；Intent Engine 若识别出此类意图，Planner 必须返回 `rejected` 并说明。
6. 必填 props 缺失即拒绝，错误信息面向用户可读。

### 5.5 回滚边界

- **可回滚**：布局、组件集合、绑定、props（存于 `ui_versions` 表）。
- **不可回滚**：报名、签到、消息记录等业务数据（独立表，版本回滚不触碰）。
- 每个版本记录：触发意图、Patch、验证结果、时间戳、父版本。

### 5.6 两种运行模式

| 模式 | 说明 | 标注 |
|---|---|---|
| 实时 AI 模式 | 调用大模型 API 解析意图并生成 Patch | 顶栏显示「AI 实时」 |
| 确定性演示模式 | 回放预先录制的真实 AI 响应（fixtures），用于评委无 Key 复现 | 顶栏显示「演示模式」，不冒充实时生成 |

## 7. 评测设计（研究生组差异化）

15 条固定测试需求（docs/eval/cases.json），对比两种实现：
A. 每轮完整重新生成界面；B. 基于当前界面生成增量 Patch。

| 指标 | 含义 |
|---|---|
| 意图解析正确率 | 识别出的能力集合与标注一致 |
| Patch 校验通过率 | 生成结果通过 Validator 的比例 |
| 数据保持率 | 变更前后业务数据条数与内容一致 |
| 任务成功率 | 新工作区能完成标注的业务操作 |
| 回滚正确率 | 撤销后界面配置与前一版本一致 |
| 无关修改数 | Patch 中与意图无关的 op 数量 |
| 响应时间 | 意图输入到可交互的耗时 |

结果写入技术文档「实验」章节。**只写实际跑出来的数据。**

## 9. 过程材料纪律（25% 的分在这里）

1. **Git**：每个功能点一次提交，信息格式 `feat(scope): 描述 [prompt-NN]`，NN 对应 docs/prompts 中的记录。禁止一次性大提交。
2. **Prompt 记录**：每次与 Claude Code 的会话结束后，立即导出到 `docs/prompts/NN-主题.md`，包含我的提问、AI 的方案、我的纠正、最终落地的提交哈希。
3. **三条必交 Prompt 链**：
   - 链 1：Patch 协议与 bindings 层的生成、AI 第一次把绑定做成硬编码数据源后如何被引导改为端口模型。
   - 链 2：Morph Diff 与版本回滚，AI 最初把业务数据一并回滚后如何被引导划清边界。
   - 链 3：Validator 拒绝案例，AI 生成的 Patch 绕过校验（或校验误杀合法 Patch）的 Bug 修复过程。
4. **产品内的 AI 操作历史不是开发证据**，二者分开存放，分开陈述。
5. 技术文档「意图控制策略」一章直接引用 CLAUDE.md 与 Schema 作为上下文约束证据。

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| bindings 层做不出来，退化为模板选择 | D3 优先做端口模型，D2 组件定义时就带端口声明 |
| AI 输出 Patch 不稳定 | Schema + few-shot + 失败重试一次 + 演示模式兜底 |
| 范围失控 | P1 只做一条规则，P2 零代码；D5 晚上冻结功能 |
| 评委无 API Key | 确定性演示模式 + README 第一行说明 |
| 评测没时间做 | 15 条用例脚本化，D6 一个下午跑完；跑不完就写明未完成，不编数据 |
| 伪功能被识破 | 模拟发送通道、演示模式均在界面明确标注 |
