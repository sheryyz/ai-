# ADR-0006 首版生成只实现用户明确提出的内容

- 状态：已采纳 · 2026-11-11

## 背景（真实观察）
阶段 3 首次用真实模型（`deepseek-flash`，提示词 `planner-v1.0`）执行演示句“创建一个校园讲座报名系统，包含姓名、学号、专业、手机号。”：
一轮即通过六层校验，但模型“合理扩展”了用户没要求的内容——新增“讲座场次”“已签到”“备注”三个字段、一个“现场签到”快捷操作和“签到率”指标；“专业”用了短文本，无法做分布统计；`CSVExport.filename` 写成 `讲座报名名单.csv`，下载时会变成 `.csv.csv`。

这与产品主张冲突：MorphOS 的价值是“从 1 到 N 的受控演进”。首版就塞进签到，后续“加签到”的增量演进就无从体现；评测中的“无关修改数”也会变差。

## 决定
1. 提示词升级为 `planner-v1.1`：创建时**只实现用户明确提出的字段与功能**；只有需求本身包含状态流转（如借用管理的借出 / 归还）时才加入状态字段与 QuickAction；取值有限的分类优先用 enum 并给出常见选项。
2. `CSVExport.filename` 在协议层规范化：末尾的 `.csv` 被去掉（Zod transform，附单测），而不是依赖模型。

## 结果
同一句话在 `planner-v1.1` 下生成 4 个字段（专业为 enum）、5 个组件；随后“加签到 + 未签到提醒 + 签到率”的演进一轮通过，Diff 显示 12 条旧记录的“已签到”按默认值“否”虚拟填充。

## 后果
- ✅ 首版更贴合意图，演进的每一步都可见、可解释。
- ❌ 用户描述过于简略时首版功能偏少；对策是演进本身成本很低，一句话即可补充。
