# 【虚构写作示例】如何组织一条 Prompt 迭代记录

> **本文件全部对话均为新编写的模拟练习，不是 MorphOS 开发历史，不是用户原话，不是实际测试证据。仅用于审查写作结构，不纳入真实 Prompt 索引。**
> 模拟主题：用户明确要求保留参数，AI 生成了越界变更。此主题参考已有问题类型，但下面的轮次、措辞、处理过程没有被当作真实发生。

## 模拟第 1 轮：提出可验收需求

**模拟用户：** 只把“设备列表”的标题改成“设备台账”，不改字段、筛选、排序和权限。先给我变更预览，不要直接生效。

**模拟助手：** 我会生成只修改该组件 title 的提案，并检查其他属性与当前定义一致。预览后由你决定是否批准。

## 模拟第 2 轮：指出不符合需求的结果

**模拟用户：** 预览里还改了表格排序。我没有要求这个改动，先别批准，检查为什么没有被拦住。

**模拟助手：** 这个提案可能符合通用协议，但不符合本次允许修改的范围。我计划把“只允许改 title”作为单次约束，在生成后和批准前分别验证，而不是只在提示词里提醒模型。

> 注意：以上是拟议改进的示例，不代表当前代码已经实现任意属性的单次硬约束。

## 模拟第 3 轮：要求有证据的验证

**模拟用户：** 加入合法标题修改、越界排序修改、过期版本和数据保留四个检查。把失败和修复后的实际输出一起留下。

**模拟助手：** 我会记录命令、版本和未经改写的输出；没有运行的检查标为未运行。

## 示例结果表：待实际执行

| 拟验证项 | 预期 | 实际结果 |
|---|---|---|
| 只改标题 | 允许进入待批准状态 | 未运行 |

| 批准标题修改 | 业务记录逐条保持 | 未运行 |

**不要把“未运行”自行替换成“通过”，也不要把这里的模拟对话移到真实记录目录并去掉标签。** 如果以后真实实施此功能，应以届时的原始导出替换整份示例，而不是追认这份示例为历史。
